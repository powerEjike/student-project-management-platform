# Product direction — user clarification, 20 October 2026

This clarification takes precedence over broader features inferred from the requirements document.

The main workflow is:

1. Admin imports final-year student records, including registration number and CGPA.
2. HOD assigns students to department lecturers, individually or as a reviewed distribution.
3. The supervisor receives an allocation notification and sees their students' names, registration numbers and CGPAs.
4. The supervisor explicitly creates each student's folder.
5. The supervisor enters the agreed topic. Archive matching runs while entering it; an exact match blocks saving. A revised topic is checked again and preserves existing progress.
6. The supervisor reviews submitted soft copies and updates project stages. The HOD sees those updates.
7. Completed work feeds the existing defence list; final completion and archive history remain available separately.

Keep the HOD dashboard focused on Students, Progress and Defence. Keep the supervisor dashboard focused on assigned students and folder actions. Attendance/contact history is presented only to the HOD. The archive supports topic checking behind the scenes; do not display archive management or browsing on either main dashboard.

Use short labels and concise instructions. Do not add policy panels, compliance explanations, digests, audit feeds, workflow guides or speculative features to the normal task screens. Existing records are retained; hiding the old screens is not deletion of their data.

Allocation uses an internal project record for access and routing. The new folder-created timestamp records the supervisor's explicit folder action; allocation alone no longer presents an opened folder. Existing topics, milestones and completed folders remain accessible without backfilling or recreating them.

Shared original-file storage remains disabled under the user's billing decision. The Documents tab supports local PDF/Word review and saved comments/receipt metadata; it does not claim that the original file is uploaded or available on another device.

Rules changes allow only the current primary supervisor to create a folder once and revise an active approved topic with an immutable topic audit. Topic revisions cannot change allocation, milestone status/deadlines, defence readiness or final completion. Existing role and department boundaries remain.

Bulk allocation improvement: the HOD can select all filtered unassigned students, select participating lecturers, and optionally set each lecturer’s maximum total active primary workload for this proposal. Blank means unlimited; zero prevents new allocations without altering existing students. An insufficient or invalid limit blocks the whole proposal. The paged preview includes registration numbers and CGPAs, plus current/new/total workload. Limits and displayed student details are part of the review fingerprint and fresh server preflight. These are proposal limits, not department-wide capacity reservations: concurrent allocations after preflight are not locked globally. Existing per-student transactions still prevent overwriting a competing initial allocation; partial failures retain completed assignments and require a fresh proposal for remaining students. No Firestore rules changes.

Staff chat opens from a floating bottom-right message button for HODs and lecturers. The unread badge remains available across workspace pages. Opening the panel leaves the workspace mounted; minimizing preserves the selected conversation and unsent draft in memory. Minimized chat does not mark incoming messages as read. Project links minimize the panel and open the authorized folder. The panel is responsive, supports Escape/minimize and restores launcher focus. Existing department/private-chat access and message rules are unchanged.

Staff chat search: filter existing authorized conversations by colleague/group names, and search active department colleagues when starting one-to-one or group conversations. Group selections remain visible and selected across searches, with a clear-selection action and existing seven-colleague maximum. Search does not grant additional directory or message access.

Student portal (project records are read-only): students create their own Firebase Auth account using the email recorded on the roster and verify that email. Super Admin enables/disables that email in Students → Student portal access. Each email is bound to one roster identity; existing bindings cannot be moved to another student. A changed roster email immediately invalidates the old address’s portal data access. No live accounts or invitations are created as part of development.

The supervisor uses Topic & progress → Publish student update to share a snapshot of the current supervisor, topic, status and sanitized stages, plus deliberately written student-facing feedback. This is a reviewed publication, not automatic sharing of private staff feedback. The portal shows its publication time; later staff changes appear only after publishing another update. Milestone notes, decision notes, abstracts, attendance, staff chat and full project documents are excluded. Separate studentPortalAccess/studentPortalViews rules permit only verified linked students to get their own published view; no listing of all student views or editing of published data. Staff project permissions remain unchanged. Shared file uploads remain unavailable while billing is disabled.

Student self-registration now requires an administrator decision. Signup collects the student’s name, registration number, current academic session and department, creates a Pending studentAccountRequests document under that authenticated UID, and sends email verification. Existing accounts without a request can submit one from the portal. No request or verified email alone grants project access. The Super Admin sees a live in-app pending-request notice on every administration page and a Student approvals section; automatic administrator email delivery is not configured.

Approval matches registration key and current session to an existing roster entry. The administrator explicitly confirms identity and the account email. Approval atomically records the decision, links studentPortalAccess to that exact request UID, and corrects the roster contact email with the existing immutable email-history record when needed. A request cannot change or approve itself. Rejection preserves the submitted details and gives the student the decision note, with no project access. Approved access can be disabled/restored by the administrator; creating a new account does not inherit another UID’s approval. All student project reads still require email verification and the approved UID/email/roster linkage. Private staff data remains excluded. These changes supersede the earlier pre-enablement workflow; each new signup is reviewed through the request queue.

Student replies to published feedback: approved students with verified emails can send a reply of up to 2,000 characters to the current published supervisor feedback. Each immutable reply keeps the student UID/name, message, original published feedback text and exact publication timestamp. Students can read their own reply history; currently authorized supervisors/co-supervisors and the HOD can read it in the student folder. Former supervisors, unrelated staff, administrators without project access and disabled student accounts cannot read these replies. Students do not gain access to private staff feedback or project editing.

Replies appear under My replies in the student portal and Student replies in Topic & progress. If a newer update arrives while composing, the draft is preserved but sending pauses until the student reviews the new feedback. The write transaction and Firestore rules also reject stale feedback editions. Reply history retains the old feedback context after later publications. No file attachments or automatic email delivery are added.

HOD overview: quick views show department-wide totals across all sessions for unassigned students, awaiting folders, overdue projects and defence-ready students. Quick views reset list filters; defence opens the existing defence list. Student and progress lists combine session, supervisor, lifecycle status and name/registration/topic/supervisor search. Overdue counts each active project once, excludes completed stages and uses Nigerian calendar dates. No new permissions or record writes are introduced.

HOD progress rows show the next unfinished template stage, its status/deadline and last recorded supervisor update in Nigerian time. A next-stage filter combines with existing list filters. Archived, defence-cleared and release-paused projects have no next active stage. Missing timestamps remain unknown; no dates are invented.

HOD progress report: Download progress Excel exports every student matching the current progress filters across all pages. The report includes filter context and Lagos generation time, roster identity/session/programme, supervisor, topic/status, completed and total stages, next stage/status/deadline and recorded update date. Private notes, email, attendance and student CGPA are excluded. This is a local download; it does not update records or send reports.

HOD Workload tab compares lecturer primary and co-supervision counts by academic session. Reuses existing allocation workload definition: pending-release and defence-ready work remain in primary load; archived and withheld work are excluded. Active directory lecturers, including those with zero students, appear first sorted by lowest primary workload; former lecturers remain visible but unavailable for new allocations. Counts are scoped to roster students in the selected session. Awaiting-folder, overdue-project and valid defence-ready counts link to matching student lists while retaining session. Allocate unassigned students opens the existing reviewed allocation flow without making changes. This is a read-only overview; no automatic reallocation, new limits or new permissions.

Simplified student approvals: Pending/Approved/Rejected views with name, registration, email and session search. The review suggests a uniquely named department and a unique registration match, preferring the requested session; ambiguous records require selection. Roster loading and failures are distinct from a missing match. Approval requires identity confirmation; any changed request/roster identity clears confirmation and the transaction rechecks the reviewed details. Admin may explicitly use the selected roster's session during approval of a mistyped-session request. The original session is retained as submittedSession with sessionCorrected=true; the registration key/email cannot be altered by this operation. Firestore rules permit this only inside an atomic admin approval with matching roster/email/access binding, never as a standalone edit, student correction or rejection rewrite. Reviewed decisions remain immutable. History shows the original and approved session. No live requests are decided during development.

Admin staffing overview: shows each department's active HOD names and lecturer count with Staff assigned, Needs HOD, Needs lecturers or Needs HOD and lecturers. Inactive staff and platform admins do not satisfy department staffing counts. Search/filter setup gaps and open the existing staff-management section prefiltered to that department. Staff directory now supports name/department search, department (including platform and missing assignments), role and active/inactive filters, with 25-row paging and clear filters. Uses authoritative department names rather than stale staff display labels. Verified-data gates hide stale directory rows after load failures. Existing access editor/self-protection, audit writes and provisioning workflow remain unchanged. No Firestore rules changes or automatic staff/account decisions.

Admin Student records now opens with a read-only department roster browser. Select academic session, search name/registration (including punctuation-normalized registration searches), or filter CGPA missing/invalid and missing admission-session records. Academic session and admission session are distinct columns; CGPA zero is valid and displayed as0.00. Records are paged25 at a time. Department changes/load failures clear or hide old rows; retry is available on read errors. Existing upload, approved portal access and email-maintenance tools remain mounted in collapsible sections, preserving their own form drafts while collapsed. No project/allocation data is read by admin and no automatic record corrections, account decisions or rules changes are introduced.

Active academic sessions: Super Admin uses Academic sessions to set a consecutive year pair per department. The private academicSessions setting and immutable history are written atomically with registrationSessions, a public projection containing only departmentName/session. No staff identities, history, roster or project data are public. New student signup and missing-request forms use a department selector and display the configured session instead of free-text department/session inputs. Before requesting access the transaction rechecks the current published configuration; Firestore rules require the configured department ID/name/session on new requests. Unconfigured departments cannot accept new self-registration requests. Existing accounts and requests retain their sessions, including the audited admin correction path for legacy mistyped sessions. Only Super Admin can save a configuration; stale saves and unaudited/public-only edits are rejected. Session changes do not promote students, change admission dates, approve requests or alter project access.

Reviewed roster corrections: Super Admin can use Correct record in the roster browser to correct student name, current CGPA (0–5) and admission session (consecutive years no later than academic session). Optional CGPA/admission data can be cleared if unconfirmed. A reason, before/after review and explicit confirmation precede saving. The transaction rechecks relevant identity fields and the last correction revision; stale edits are blocked in the UI and store. Each correction atomically appends immutable admin-only rosterCorrections history containing before/after values, reason, actor and time. Existing email audits remain separate. Rules allow no registration number/key, department, current academic session, programme, email, allocation or project changes through this operation. Prior published snapshots and historical documents are not rewritten. No real roster corrections are performed as part of feature validation. This supersedes the roster browser's earlier read-only limitation for these three fields only.

Roster import history: Admin Student records includes a collapsed history viewer. New uploads group immutable ten-student batch receipts by run and source label, including all-skipped imports. Filters apply to loaded history; partial groups never claim completion. Legacy receipts remain separate because original file grouping cannot be reconstructed. History does not store the original file or change student records.

Admin roster download: Download roster Excel exports all students matching the selected department and current roster filters across every page. Includes name, registration number, CGPA, academic session, admission session, programme and level, with filter context and Lagos generation time. Text registrations and literal strings are retained; missing/invalid scores are labelled. Email and private project data are excluded. Local download only; no Firestore rules changes or record writes.

Supervisor folder simplification: progress stages collapse to name/status/deadline summaries. The next unfinished stage of active work opens by default; any stage can be opened for review/update, with existing authorization and save behavior. Collapsing a stage preserves its draft. Topic/progress stays mounted across folder tabs, retaining in-memory drafts when opening Documents or Defence; leaving the folder/reloading still clears drafts, and existing remote-change reset behavior remains. No Firestore rules or stored data changes.

Document review simplification: the document viewer, adding comments and saved comments come first. Submission register, revision comparison, email preparation, examiner export and earlier-version remark tools are grouped under More review tools, mounted on first open and retained while collapsed. Existing roles, safeguards and save/export behavior remain. Saved comments combine all-word case-insensitive Unicode text search with page/type filters across the full loaded review; paging resets on filter changes. Opening a different local document clears those filters. Original files remain local; billing and Firestore rules unchanged.

Document comment draft protection: a nonblank unfinished comment stays bound to its original passage/page while browsing pages or saved remarks. Selecting another passage or clearing the selection cannot silently move it; choose Save or Discard comment first. Opening another local file is disabled until resolved. Selection changes and area-description edits are blocked during saving. Drafts remain in memory only; folder exit/reload protection and persisted draft storage are not added. Existing comment save, role and Firestore rules remain unchanged.

HOD single-supervisor assignment review: selected students now receive a paged before/after review with registration, CGPA and academic session, primary workload totals, required reason and explicit confirmation. Existing co-supervisors are preserved; choosing the co-supervisor as new primary explicitly clears the co role. Same-primary allocations are skipped. Completed, defence-cleared, pending-release and withheld selections are blocked. Reviewed identity/allocation fields and revision are rechecked in each student transaction, with current target lecturer availability. Live changes reset confirmation; partial failures retain completed assignments and close review for a fresh proposal. Original folder/topic/progress/history are preserved. Workload counts are advisory, not reserved capacity. Existing role and Firestore rules remain unchanged; no live assignments are made during validation.

Student portal overview: the latest published update shows supervisor, academic session, topic/status and actual Lagos publication time (missing times stay unknown). Progress shows completed/total and percentage with the next unfinished published stage; completed/archived projects show no next task. Full stages are expandable. Feedback and reply composer share one section, with earlier replies expandable; existing edition checks and reply access remain. Publication loading, errors with retry and a genuinely missing update are distinct; a response for another student ID is hidden. Access-check failures have their own retry and do not show approval/pending claims. These are supervisor-published snapshots, not live private project data; no new public fields or Firestore rules changes.

Class attendance (separate from supervision contact history): every active department lecturer and HOD can open their own class with title, academic session and a 2–30 minute window. Class attendance navigation shows own sessions for lecturers and department sessions for HODs, with name/date filters and up to 200 latest sessions. Only the creating lecturer can rotate codes or close their session; HOD oversight does not allow controlling another lecturer's session. QR/link codes use 128-bit random tokens, rotate every45seconds while displayed, and are rejected by server rules after60seconds, session closure/expiry or host access revocation. Codes are private to the owner and students cannot list sessions or retrieve live secrets. QR links open student sign-in with the code retained; native phone camera scanning or pasted codes are supported (no embedded camera scanner). Verified, approved, actively bound students in the matching department and current roster academic session explicitly confirm presence. Immutable check-ins are keyed by roster studentId, not email/UID, with authenticated UID, approved request identity and server time; existing entries cannot be duplicated or edited even after an account rebinding. Students can read only their own receipt; owner and department HOD can read registers. No automatic absences, device/location tracking, biometrics or physical-presence guarantees. A code/account can still be shared; staff spot-checks remain necessary. Billing remains disabled, no Functions or Storage enabled. Rules and two indexes added. The old HOD folder Attendance tab is now Contact history; its existing permissions and data are unchanged.

Attendance scope clarified: all approved undergraduate Biochemistry students from100 through400level may check in, without a project allocation, topic or folder. Attendance eligibility remains department+academic-session+approved/verified account; no final-year condition is imposed. Admin imports one level per upload using an explicit100/200/300/400 selector (400 retains the existing Final year stored label). Recognized100–300 students are omitted from unassigned project workspace lists; existing project folders remain accessible and unknown legacy level labels are preserved. Lower-level students cannot use the normal project assignment review. The student home is labelled Student portal; no published project does not block attendance. No real roster imports or level changes are performed.

2026-10-22 class reporting: each class lasts two hours from its server-recorded start, independent of the shorter check-in window. Closing check-in early does not finish class. Only its owner can generate the attendance Excel after two hours. Registers stay private to the lecturer until they explicitly choose Send to HOD after generation; HOD can then view/download through Class attendance. Sharing is one-way, server-timestamped, and does not send email. HOD can still run their own classes. This supersedes automatic department-wide HOD attendance visibility. Existing student eligibility and short-code rules remain.

Lecturer attendance history: course/class selector groups existing titles by case and repeated whitespace, plus academic session, inclusive Lagos class-start dates, report status and all-word search. Filters combine before 25-row pagination and newest-first ordering. History starts with the latest 200 permitted sessions; Load older classes expands the listener by 200 while preserving filters and the selected register. Counts explicitly describe loaded records, not all-time totals. Existing owner and explicitly shared HOD queries remain scoped; no rules changes or live attendance edits. Open register / report reuses the existing register, Excel generation/download and optional HOD-sharing actions.

Student attendance history: approved verified roster-bound students may query only their own immutable check-ins across class sessions using studentId-constrained collection-group queries. A current approved binding can read its own earlier receipts/class metadata after an academic-session change or approved account rebinding. Unrestricted, peer, unverified, recreated and revoked identities remain denied; no raw student/project or class-list access added. Student portal shows My attendance history with normalized course and academic-session selectors, inclusive Lagos check-in dates, newest-first25paging, initial100records and Load older check-ins increments100 while keeping filters. Counts describe loaded records; missing metadata leaves the receipt/time visible with retry. Existing records are used without a production backfill or added writes. No absence/percentage claims or sharing of student history.
